# bench —— sweet 的吞吐基准

## 这个基准能证明什么，不能证明什么

能证明：sweet 相对裸 grpc-go 的**每调用开销**（同一台机器、同一形状、交错跑）。

不能证明：协议优劣。和 jaws 的表并排时，一次比较同时换了语言运行时、网络库、协议实现与序列化，
差值只能记成**栈 vs 栈**。谁把它说成"gRPC 比 wire 快/慢"，就是没控制变量。

口径与 jaws 的 `doc/benchmark.md` 对齐：闭环、固定并发、预热丢弃、延迟合并取分位、
provider 与 consumer 分进程（对应 jaws 的 `ROLE=provider` / `ROLE=consumer`）、loopback TCP。
payload 同为 `HelloRequest{name="benchmark"}`，回复文本等长。并发 20、预热 5s、测量 15s 或 40s，
与 jaws 表里 `THREADS=20 WARMUP=5 DURATION=40` 同形。

## 跑法

```
# 终端 1
go run ./bench -mode provider -server sweet -port 50051

# 终端 2
go run ./bench -mode consumer -client sweet -addr 127.0.0.1:50051 -threads 20 -warmup 5 -duration 40
```

`-server` / `-client` 各取 `native`（裸 grpc-go）或 `sweet`，四组组合都在下面。跨语言那格把
provider 换成 jaws 的：

```
cd /path/to/jaws && ROLE=provider SERVER=wire PORT=50051 ./run-sample.sh bench-grpc
```

## 环境

Apple M2（8 核）、go1.27.3 darwin/arm64、grpc-go v1.84.0、loopback、单条客户端连接上 20 个并发
调用。测量日期 2026-10-29。jaws 侧数字取自其 `doc/benchmark.md`（2026-09-25 记录，同为 macOS
aarch64 8 核），**未重跑**。

## 先说方法学结论：不交错就是假的

同一台机器持续负载下会漂。首回合吃到冷启动红利，之后落到稳定值：

| 轮次 | native↔native | sweet↔sweet |
| --- | --- | --- |
| 1 | 102,146 | 89,021 |
| 2 | 85,596 | 82,584 |
| 3 | 87,290 | 87,632 |
| 4 | 87,763 | 88,606 |

单次 40s 各跑一遍会得出 `105,502 vs 105,793`，看着"完全持平"；不交错连跑三次则 native 一路
105,496 → 101,066 → 99,715、sweet 一路 89,957 → 83,925 → 83,864，会误判成"sweet 慢 15%"。
只有 A/B/A/B 交错之后差异才塌缩：**稳定态两臂都在 83k–89k 区间重叠，sweet 的每调用开销落在
噪声里**——符合预期，`Register`/`Dial` 只作用于建连与订阅，不在每调用路径上。

结论：**任何单次数字都不要引用**；要引用就引交错后的中位数，并写明时长。

## 并发度扫描：饱和平台、崩塌点，以及为什么不报"峰值"

jaws 表里的 142,876 绑的是 20 线程、分进程（它那条"25 线程降到 98,785"取自同进程配置，与它
自己的分进程口径不是一回事，见后文约束 2）。Go 侧要有自己的报告点，就得自己扫；一开始只按倍增扫
（20/40/80/160/320/640），据此写"峰值在 320"
是错的：320→640 跨度太大，而 640 的单遍结果（152,863）比 320 的中位数还高，差值全在噪声里。

加密到 160–640（native 臂，每点 3 遍取中位）后，形状是**平台**而不是尖峰：

| threads | 中位 QPS | P50 | P99 |
| --- | --- | --- | --- |
| 80 | 144,094 | 505 us | 1,204 us |
| 160 | 153,252 | 995 us | 2,068 us |
| 240 | 152,428 | — | — |
| 320 | 154,009 | — | — |
| 400 | 154,260 | 2,500 us | 4,185 us |
| 480 | 151,043 | — | — |
| 560 | 131,104 | — | — |
| 640 | 131,709 | 44,238 us(max) | 5,950 us |

160–480 之间 151k–154k，跨度小于本机 ±8% 的噪声，所以"峰值到底在 320 还是 400"这个问题
**问不出答案**，能确定的只有：饱和平台约 160–480，560 起明显塌到 ~131k（-14%，3 遍各自聚簇，
这个差是真的）。

带延迟再看，工作点更该选平台低端：**160 线程 151k，P50 1.0ms；400 线程 153k，P50 2.5ms**
——多花 2.5 倍并发换 1.4% 吞吐，不划算。所以本文件引用数字时以 **160 线程**为报告点，
不引用"最大 QPS"。

sweet 与 native 在每个点位都在一起（80：142,680 vs 144,094；160：150,499 vs 152,087；
400：153,311 vs 153,147），最大偏离 1%。结合前面 320 档 6+6 样本中位数 150.4k vs 150.5k：
**sweet 的每调用开销在本机分辨率（±8%）下测不出来**。

## 跨语言那一格

Go 客户端 → jaws 的 wire benchmark provider（静默实现），交错两轮：

| 轮次 | native client | sweet client |
| --- | --- | --- |
| 1 | 95,147 | 96,942 |
| 2 | 97,866 | 97,478 |

全部 0 错误。对照 jaws 表里同一服务端的 `grpc-java → wire = 104,967`：**同一 Java 服务端，
Go 客户端与 Java 客户端在同一量级**，差值在跨天、跨机况的范围内，不构成结论。

一个必须记的反例：把 provider 换成 `jaws-sample-wire-boot-provider`，同一客户端只跑到
**约 39.3k–39.8k**。原因是它的 `sayHello` 每次调用都 `log.info` 一行（
`GreeterServiceImpl.java:35`）。这不是协议差异，是被测服务端自己加了 IO——跨语言比吞吐时
必须确认两端 handler 都是静默的。

## 与 jaws 整表并排（栈 vs 栈）

| 组合 | QPS | 来源 |
| --- | --- | --- |
| grpc-go ↔ grpc-go（sweet 路径，**20 线程**） | 100,661 – 103,962 | 本文，2026-10-29，交错 |
| grpc-go ↔ grpc-go（sweet 路径，**160 线程**报告点） | 150,499 | 本文，同上 |
| grpc-go → jaws wire | 95k–98k | 本文，2026-10-29，交错 |
| grpc-java → grpc-java | 70,334 | jaws `doc/benchmark.md`，2026-09-25 |
| grpc-java → jaws wire | 104,967 | 同上 |
| jaws wire → jaws wire | 89,945 / 92,423(direct) | 同上 |
| jaws TCP → jaws TCP | 峰值 142,876 / 均值 140,692（20 线程） | 同上 |

读法有三条约束，少一条这表就会骗人：

1. **同点位才可比**。jaws 全部数字锁在 20 线程（那边已量过多次，不再重测），所以第一行
   （20 线程 100k–104k）是本页与它并排的唯一格子。150k 那一行只是 Go 侧自己的报告点，
   **不用来跟 142,876 比大小**。
2. **不拿 jaws 的历史并发扫描做曲线形状结论**。`doc/benchmark.md` 那张 4/10/16/20/25 =
   62,314 / 93,694 / 97,363 / 100,408 / 98,785 是**同进程 `ROLE=all`、单条连接多路复用、
   DURATION=10s、且 09-06 写路径异步化之前**的基线，其 20 线程档本身就写着"同进程内已有 40+
   活跃线程"。本页 Go 数字是**分进程、单连接、8–12s、交错重复**，两边配置不可对齐，
   "Java 20 见底而 Go 要 160 才饱和"这种话不写——那是拿不同口径的曲线比形状。
3. Go↔Go 与 Java↔Java 不同日、不共享校准，看量级不作差。表里唯一在同一服务端上做过的对照，
   是"同一 jaws wire 服务端：Go 客户端 95k–98k vs Java 客户端 104,967"，跨天问题仍在。
   另一条巧合值得记：Go↔Go 在 20 线程约 104k，与 Java 侧 `grpc-java → jaws wire` 的 104,967
   撞在同一个数字上——但两者服务端栈不同（grpc-go vs Netty+自研 wire）、日期不同，只能算量级巧合。
